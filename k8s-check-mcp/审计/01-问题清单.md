# K8s Check MCP Server 代码审计 — 问题清单

> 审计日期：2026-06-04  
> 审计文件：`mcp_server.py`（~1180 行）  
> 审计范围：代码正确性、安全性、性能、健壮性、代码风格

---

## 一、Bug（会导致错误行为）

### 1. Init Container 资源计算错误

**位置：** `_pod_effective_resources()` 函数（原 line 502-512）

**问题：** 对 init containers 的资源做了 **求和** (`_sum_container_resources`)，但 Kubernetes 调度器对 init containers 采用的是 **逐个 container 取最大值** 的逻辑（因为 init containers 串行执行，不会同时占用资源）。

```python
# 错误：对所有 init containers 求和
i_req_cpu, i_lim_cpu, i_req_mem, i_lim_mem = _sum_container_resources(init_containers)

# 正确：对每个 init container 取各资源维度的 max
i_req_cpu = max((_cpu_to_millicores(...) for c in init_containers), default=0)
```

**影响：** 如果 Pod 有多个 init containers，资源审计结果会偏高，可能误报 overcommit。

**严重程度：** 高

---

### 2. 每次工具调用都重新初始化 K8s 客户端

**位置：** `list_nodes`、`get_node_detail`、`get_node_resource_usage` 等 7 个 tool/resource 函数

**问题：** 每个 MCP tool 调用都执行 `init_k8s_client()`，每次都重新：
- 读取 kubeconfig 文件
- 创建新的 `ApiClient`、`CoreV1Api`、`CustomObjectsApi` 对象

LLM 在一次排障对话中通常会连续调用多个工具，这导致了大量重复的配置加载和对象创建开销。

**严重程度：** 中（性能）

---

### 3. 速率限制器全局单例存在竞态条件

**位置：** `_get_api_limiter()` 函数（原 line 160-169）

**问题：** 经典 check-then-act 竞态条件：

```python
def _get_api_limiter():
    global _API_LIMITER
    if _API_LIMITER is not None:  # check
        return _API_LIMITER
    # ... 另一个线程可能同时到达此处
    _API_LIMITER = _TokenBucketLimiter(...)  # act
```

**影响：** 两个线程可能同时创建实例，虽然后一个会被 GC 回收，不是 catastrophic bug，但不符合线程安全最佳实践。

**严重程度：** 低

## 二、安全隐患

### 4. SSL 证书校验默认关闭

**位置：** `init_k8s_client()` 函数（原 line 264）

```python
verify_ssl = _env_bool("MCP_K8S_VERIFY_SSL", False)
```

**问题：** 默认不验证 API Server 的 TLS 证书，存在中间人攻击风险。安全敏感的配置应该默认开启，由用户在测试环境中显式关闭。

**严重程度：** 中

---

### 5. `_read_pod_log_excerpt` 使用裸 `except Exception`

**位置：** `_read_pod_log_excerpt()` 函数（原 line 1039）

```python
except ApiException:
    continue
except Exception:     # 吞掉所有异常，包括编程错误
    continue
```

**问题：** 裸 `except Exception` 会吞掉 `AttributeError`、`TypeError` 等编程错误，导致调试困难。

**严重程度：** 低

---

## 三、性能问题

### 6. `_get_runtime_config()` 每次调用都重新解析配置

**位置：** 多个 tool 函数中调用

**问题：** 如果使用了 `MCP_CONFIG` JSON/YAML 配置文件，每次 tool 调用都会重新读盘并解析。阈值配置在一次运行中不会变化，没有理由每次重新读取。

**严重程度：** 中

---

### 7. `_pod_basic_view` 和 `_pod_issue_summary` 重复计算 Pod 异常

**位置：** `_pod_basic_view()`（原 line 543）+ `list_node_pods()`（原 line 994）

**问题：**
- `_pod_basic_view` 内部调用了 `_pod_issue(pod, restart_threshold=0)`
- `list_node_pods` 中又对同一个 pod 调用了 `_pod_issue_summary`，后者内部再次调用 `_pod_issue`

每个 Pod 的容器状态被遍历了两遍。

**严重程度：** 低

---

### 8. `get_node_resource_usage` 对所有 Pod 构建完整 breakdown 但只返回前 50 个

**位置：** `get_node_resource_usage()` 函数（原 line 923）

**问题：** 如果节点上有 1000+ Pod，仍在内存中构建 1000 个字典对象后通过 `[:50]` 截断。可以在超过 50 个后停止追加。

**严重程度：** 低

---

## 四、健壮性与可观测性

### 9. 完全没有日志

**问题：** 代码中没有任何 logging 语句。以下场景对运维完全不可见：
- K8s API 调用失败
- metrics-server 不可用（静默降级）
- 配置加载异常
- 服务启动/停止

**严重程度：** 中

---

### 10. 缺少健康检查机制

**问题：** 如果 K8s API 不可达，MCP client 无法提前知道，只有等 LLM 调用工具时才会暴露错误。缺少主动探测连接状态的能力。

**严重程度：** 低

---

### 11. `parse_quantity` 对无数字前缀的输入会崩溃

**位置：** `parse_quantity()` 函数（原 line 332-350）

**问题：** 如果传入纯单位字符串如 `"m"`（不带数字前缀，如 `"250m"`），后缀匹配成功但 `s[:-len(suf)]` 得到空字符串，`float("")` 会抛出 `ValueError`。虽然 K8s API 正常不会返回这种值，但作为通用解析函数应具备防御性。

**严重程度：** 低

---

## 五、代码质量与风格

### 12. `verify_ssl` 设置时机

**位置：** `init_k8s_client()` 函数（原 line 273-275）

**问题：** `get_default_copy()` 在 `load_kube_config` / `load_incluster_config` 之后调用。虽然当前逻辑能正常工作，但配置加载与修改的顺序关系不够清晰，给后续维护留下隐患。

**严重程度：** 低

---

### 13. README 文件名与实际不符

**位置：** `README.md` 多处

**问题：** README 中引用的文件名是 `k8s_inspector/mcp_server.py` 和 `requirements-mcp.txt`，但实际项目结构是平铺的 `mcp_server.py` 和 `requirements.txt`。新用户按 README 操作会失败。

**严重程度：** 中

---

### 14. `_format_age` 对负时间差处理不完善

**位置：** `_format_age()` 函数（原 line 289-299）

**问题：** 如果存在时钟偏移导致 `total_seconds < 0`，`max(total_seconds // 60, 0)` 会静默返回 `"0m"`，不够明确。

**严重程度：** 低
